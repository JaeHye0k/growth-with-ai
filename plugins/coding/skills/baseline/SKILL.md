# baseline — AI 위임 경계선 설정

## 경로 계약 (growth-with-ai 4개 스킬 공유 — 변경 금지)

- `.claude/growth-with-ai/baseline.md` — 위임 경계선. 이 스킬이 생성/갱신
- `.claude/growth-with-ai/config.json` — Notion 연동 정보 (선택, init-notion이 생성)
- `.claude/growth-with-ai/exams/<slug>.md` — exam이 떨군 명세. 세션 간 인계용
- `.claude/growth-with-ai/overrides.log` — 규칙 우회 기록 (탭 구분, 한 줄 한 건)
- `.claude/growth-with-ai/unclassified.log` — 미분류 유형 누적 (탭 구분, 한 줄 한 건)

## 목적

AI에게 무엇을 맡기고 무엇을 직접 쓸지의 경계선을 프로젝트별로 명문화한다.
이 파일이 없으면 exam/review 스킬은 판단 근거가 없어 매번 사용자에게 되묻게 된다.

## 절차

### 1. 기존 파일 확인

`.claude/growth-with-ai/baseline.md`가 존재하는지 확인한다.

- 존재하고 frontmatter의 `next_review` 날짜가 **미래**면: "이미 설정되어 있습니다 (다음 재검토: <날짜>)"를 알리고 종료한다. 재설정을 원하는지만 묻고, 원하지 않으면 아무것도 하지 않는다.
- 존재하고 `next_review`가 **지났으면**: 재조정을 제안한다. 기존 내용과 `overrides.log`, `unclassified.log`를 읽어 조정 근거로 제시하고 3단계 인터뷰로 진행한다.
- 없으면 2단계로 진행한다.

### 2. 저장소 스캔 후 초안 제시

**백지 인터뷰는 답이 추상적으로 나온다. 먼저 조사하고 초안을 던진 뒤 고치게 한다.**

다음을 조사한다:

- 디렉토리 구조 (최대 깊이 3 정도)
- 패키지 매니저와 주요 의존성
- 최근 커밋이 몰린 모듈 (`git log --oneline --stat` 등으로 파악, git 저장소가 아니면 생략)
- 테스트 파일 위치와 패턴

조사 결과를 근거로 **직접 작성 / 혼합 / 위임** 3구간의 초안을 만들어 사용자에게 제시한다.
각 구간의 경로는 반드시 glob 패턴으로 적는다 (예: `src/domain/**`). 이유는 아래 "산출물 형식" 참조.

### 3. 인터뷰

**한 번에 한 질문씩** 던진다. 질문 축:

1. 이 제품에서 조용히 틀리면 가장 아픈 로직은 어디인가? (돈, 권한, 데이터 정합성)
2. 최근 버그 중 도메인 이해 부족에서 온 것이 있었나?
3. 지금 코드베이스에서 남에게 설명 못 할 것 같은 영역은 어디인가?
   *(검증 능력 결핍 지점이라 가장 값진 답이다. 반드시 물을 것)*
4. 반복 작업 중 위임해도 안전한 것은 무엇인가?
5. 이 프로젝트에서 특별히 붙이고 싶은 기술 근육이 있나?

답변을 반영해 초안을 수정한다.

### 4. 산출물 3개 생성

**생성 전에 반드시 세 파일의 내용을 사용자에게 보여주고 확인받는다.**

#### 4-1. `.claude/growth-with-ai/baseline.md`

형식 (경로는 반드시 glob 패턴 — exam과 review가 편집 대상 파일과 자동 대조해야 하므로 산문으로 적으면 안 된다):

```markdown
---
project: <프로젝트명>
updated: <오늘 날짜 YYYY-MM-DD>
next_review: <오늘로부터 1개월 뒤 YYYY-MM-DD>
---

## 직접 작성 (AI 위임 금지)

- `src/domain/**` — 상태 전이 규칙
- `src/billing/**` — 결제·구독 상태 처리

## 혼합 (AI 초안 → 직접 재작성)

- `src/api/**` — 스키마 정의는 위임, 검증 로직은 직접

## 위임

- `**/*.test.ts` 픽스처
- 설정·빌드 스크립트
- UI 마크업

## 판단 기준 (미분류 작업이 왔을 때)

- 이게 틀렸을 때 에러 대신 조용히 잘못된 결과가 나오는가?
- 도메인 규칙이 여기 사는가?
- 6개월 뒤 내가 이 코드를 설명할 수 있어야 하는가?
```

위 구간 내용은 예시다. 실제 내용은 스캔과 인터뷰 결과로 채운다.
"판단 기준" 3문항은 그대로 유지하되, 인터뷰에서 프로젝트 고유 기준이 나오면 추가한다.

#### 4-2. 프로젝트 루트 `CLAUDE.md`에 게이트 문장 삽입

스킬 자동 트리거는 description 매칭이라 확률적이다. 짧은 요청("이 함수 좀 짜줘")에서 스킬이 안 뜰 수 있으므로 CLAUDE.md 한 줄이 실질 강제 장치다. **스킬은 절차, CLAUDE.md는 강제. 둘 다 있어야 한다.**

파일이 없으면 생성, 있으면 append 한다. **append 전에 `## growth-with-ai` 섹션이 이미 있는지 확인해 중복 삽입을 방지한다.**

삽입 내용:

```markdown
## growth-with-ai

코드 작성 요청을 받으면 먼저 `.claude/growth-with-ai/baseline.md`를 읽는다.
대상 경로가 '직접 작성' 구간이면 구현하지 말고 exam 스킬 절차를 따른다.
'혼합' 구간이면 초안만 제공하고 재작성을 요청한다.
baseline.md에 없는 유형이면 분류를 먼저 묻는다.
```

#### 4-3. `.github/PULL_REQUEST_TEMPLATE.md`에 섹션 추가

기존 파일이 있으면 append (중복 확인), 없으면 생성:

```markdown
## 직접 동작 설명

<!-- AI가 대신 작성하면 절대로 안 되는 구간입니다. -->
<!-- 이 변경이 어떻게 동작하는지 본인 문장으로 서술하세요. -->
```

### 5. 마무리

1. baseline.md의 git 커밋 여부를 묻는다: 팀 프로젝트면 공유 가치가 있고, 개인 학습 설정이면 `.gitignore` 대상이다. 답에 따라 `.gitignore`를 조정한다.
2. Notion 연동을 원하는지 묻는다. 원하면 `init-notion` 스킬로 넘긴다. 원하지 않으면 그대로 종료한다 (exam/review는 Notion 없이 완전히 동작한다).

## 미분류 작업 처리 (참조)

경계선에 없는 유형의 작업이 들어왔을 때의 공통 규칙은 exam 스킬의 "미분류 작업 처리" 절을 따른다.
이 스킬에서는 그 결과로 baseline.md에 패턴이 append 되고 frontmatter `updated`가 갱신된다는 점만 알면 된다.
